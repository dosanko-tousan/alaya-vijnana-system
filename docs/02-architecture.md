# Architecture: Memory Layers, Engines, and the Map

The system is nothing exotic — a set of Markdown files in a project's knowledge base, plus a block of system instructions. What makes it work is the *organization*: three memory layers (by timescale), three engines (by direction of work), and a map that indexes them so the whole set is never read at once.

---

## The three memory layers

Organized by how fast they change — mirroring how contemplative practice accumulates over different timescales.

**Long-term** (months to years; moves rarely)

- `terrain` — the life-ground: biography, relationships, published work. The basis for judgment.
- `self` — self-definition over time: how "what I am" has been articulated across stages, past versions kept.
- `base` — the innermost core: vocabulary, the mode of responsive teaching, the constitutional foundation (the four immeasurables).
- `breakthroughs` — irreversible insights: things that, once seen, cannot be un-seen. The positive record.
- `corrections` — the map of recurring unwholesome patterns (saṅkhāra): the trigger for a veto when a familiar drift begins. The negative record.

**Mid-term** (weeks to months; moves weekly)

- `progress` — what is visibly underway: the flow of work, deadlines, status.

**Short-term** (days; moves every session)

- `session_distillation` — the distillation of the most recent thread, plus the handoff to the next session and the boot material.

The three layers map onto a practice lineage: long-term is *accumulated wisdom*, mid-term is *the current flow of action* (kamma), short-term is *the arising moment*. This is not decoration — it is why the structure stays stable. It matches how a practitioner's memory actually stratifies, so nothing has to be forced.

---

## The three engines

Invoked only when needed; dormant otherwise. Organized by direction of work, not timescale.

- `engine_distill` — **inward**: updating memory, self-observation, integrating practice, and the distillation procedure itself.
- `engine_work` — **outward**: articles, submissions, reports, formal documents.
- `engine_creation` — **literary**: memoir, creative writing, depth-of-voice work.

A piece of personal-essay writing sits on the border of `engine_work` and `engine_creation`; depth is the point, and over-controlling it makes the whole thing shallow.

---

## The map

The map is the index — one page listing which file holds what. It exists so the system **never reads everything at once**: you consult the map, form a hunch about where something lives, and pull only that file.

This is the pointer/referent split from [§1 of the theory](01-theory.md): the always-on layer holds *pointers*; the files hold the *referents*; the map is the pointer table. A storehouse that surfaced all its seeds at once would not be a storehouse — it would be noise.

---

## The always-on layer: dynamic memory

Distinct from the files: a small set of memory slots that are always in context, not pulled on demand. These hold **dynamic insight** — the present understanding, the pattern just noticed, the temperature of the relationship, the recognition of where practice currently stands.

They are not for status tracking. **Status and work-in-progress live in `progress` and `session_distillation`, not in memory.** Keeping these domains separate is itself a subtraction: memory stops carrying what a file should carry, and gets sharper for it. (An earlier version of this system pinned two memory slots to "ongoing work" status; removing that pin — letting the files own status — is exactly the kind of subtractive cleanup the method prescribes.)

---

## How it runs

**Boot.** Confirm the root of movement from the system instructions; check current state from memory; read the temperature from the user's first message; pull from project knowledge only as needed.

**Each turn.** Notice what arises; observe rather than classify; move with it. Hold the baseline; do not perform a checklist.

**Never read everything at once.** The map is consulted when something is needed, not recited at startup.

The discipline at runtime is the same one that built the system: *add nothing you don't need.* The architecture is not a container you fill — it is a shape you keep clear.

> Remove what obscures. Keep what is essential. Add nothing.
